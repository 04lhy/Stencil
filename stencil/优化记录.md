## 四、编译与运行

### 编译默认优化版
```bash
make all    # 编译 bin/stencil (2x unroll + stream + prefetch)
```

### 编译其他版本
```bash
make avx2    # 逐行 kernel 版本
make block   # 分块 kernel 版本 (仅适用于窄图像)
make debug   # 调试版本 (O0)
```

### 运行
```bash
make run     # OMP_NUM_THREADS=20 OMP_PROC_BIND=spread
make check   # 验证 data.txt == check.txt
```

### 性能对比
```bash
make bench-all  # 全量对比所有版本
make scan-threads  # 扫描最优线程数
```

### 关键编译选项
- `-Ofast`: 最高级优化（含 -ffast-math）
- `-march=native`: 自动检测 CPU 指令集
- `-mavx2 -mfma`: AVX2 + FMA 指令集
- `-fopenmp`: OpenMP 多线程
- `-no-pie`: 静态库链接必需

## 六、关键技术决策

### 6.1 为什么 block kernel (读6算4) 在本环境更慢？

参考代码的"读 6 行算 4 行"策略在 EPYC 双路上有效，但在本环境 (Arrow Lake + 超宽图像) 反而慢：

1. **图像太宽 (10410 列)**：每行 ~41.6KB，3 行 ~125KB 轻松放入 L2 cache (2MB)
   → 逐行 kernel 已有最优 cache 局部性，每行只从内存加载一次

2. **Block kernel 读更多数据**：6/4 = 1.5x 内存读取 vs 逐行的 ~1x（cache 命中后）
   → 数据复用收益被额外 load 抵消

3. **Block kernel 无法用 stream store**：多行输出对齐各不相同，只能用 storeu
   → 写分配 (write-allocate) 污染 cache

4. **适用场景**：block kernel 适用于**窄图像**（行宽 >> cache line 时减少重复加载）

### 6.2 为什么 20 线程 > 24 线程？

Core Ultra 9 275HX 有 P-core（性能核）+ E-core（能效核）混合架构：
- 所有 24 核一起跑，E-core 慢拖累整体
- 20 线程是最佳平衡点（覆盖所有 P-core + 部分 E-core）
- WSL2 不暴露 hybrid 拓扑，无法精准绑定 P-core

### 6.3 为什么 OMP_PROC_BIND=spread > close？

- `spread`: 线程分散到不同物理核心，减少共享资源竞争
- `close`: 线程集中到相邻核心（可能是相邻 HT 线程），争抢 L1/L2 cache
- Arrow Lake 的 P-core 和 E-core 集群分属不同区域，spread 能更好地利用

### 6.4 2x 循环展开 + 累加式加载

关键优化：边 load 边 sum，而非加载全部 9 个向量后再计算：
```cpp
__m256 mc  = _mm256_loadu_ps(r1 + j);       // center (保留)
__m256 sum = _mm256_loadu_ps(r0 + j - 1);   // TL
sum = _mm256_add_ps(sum, _mm256_loadu_ps(r0 + j));      // + TC
// ... 边 load 边累加 ...
```
寄存器占用仅 2-3 YMM/batch，2x 展开 (16 元素/迭代) 不溢出 16 YMM 寄存器。

### 6.5 对标 IPCC 的差异分析

| 对比项 | IPCC (EPYC 7452×2) | 本实现 (Arrow Lake) |
|--------|---------------------|---------------------|
| 最终性能 | 15.8ms (64核) | 66.8ms (20线程) |
| 加速比 | 695.5x | 127.7x |
| 核数 | 64 | 24 (20 有效) |
| 每核效率 | 15.8×64 = 1011 core-ms | 66.8×20 = 1336 core-ms |
| 内存带宽 | 8-ch DDR4 ≈ 200 GB/s | 2-ch DDR5 ≈ 90 GB/s |

每核效率接近（1336 vs 1011 core-ms），差异主要来自硬件平台（核数、内存通道数）。

### 6.6 IPCC 参考实现 vs 本项目实现 对比

IPCC 官方优化代码 ([opt_kernel.h](../IPCC_stencil/src/opt_kernel.h)) 在相同硬件上跑到 **62.5ms**，比本项目最优版 (67.1ms) 快 **7%**。以下是逐项对比分析。

#### 6.6.1 代码结构对比

```
                            IPCC opt_kernel             本项目 stencil.cc
─────────────────────────────────────────────────────────────────────────────
索引方式                      1D 线性化 in[index]          逐行指针 r0+j, r1+j, r2+j
对齐处理                      一次前置对齐循环               每行检测 + 标量序言
SIMD 宽度                     8 floats (AVX2)              8 floats × 2x 展开 = 16
公式                          fmsub(8, center, MR)         fmsub(9, center, sum)
加法分组                      独立子树 (ILP 友好)           顺序累加链
Stream store                  ✅                            ✅
软件预取                      ❌                            ✅ _mm_prefetch T0
OpenMP 调度                   手动分段 (countPerThread)     #pragma omp parallel for
Scalar tail                   循环 + 寄存器 mask            标量循环逐元素
```

#### 6.6.2 加法链对比 (核心性能差异)

**IPCC 分组加法链**（4 个独立子树 → 合并）：
```cpp
// 4 条独立加法链，可并行发射
val1 = TL + TC                    // 组1: 上排左+中
val2 = TR + ML                    // 组2: 上排右+中排左
val3 = 8.0 * center - MR          // 组3: fmsub 中心-中排右
val4 = BL + BC                    // 组4: 下排左+中
val5 = BR                         // 组5: 下排右 (load only)

// 合并阶段 — 只需 3 次加法
val10 = val1 + val2               // TL+TC+TR+ML
val11 = val3 - val4               // 8*center-MR-BL-BC
val20 = val10 + val5              // TL+TC+TR+ML+BR
val   = val11 - val20             // 8*center - sum_of_8_neighbors
```
→ 依赖链深度: **load → 2 add → 1 fmsub → clamp → stream** (约 5 级)

**本项目顺序累加链**：
```cpp
sum = TL
sum += TC
sum += TR
sum += ML
sum += center     // ← 注意: center 被加入 sum
sum += MR
sum += BL
sum += BC
sum += BR
val = 9 * center - sum   // = 9*center - (center + 8_neighbors) = 8*center - 8_neighbors
```
→ 依赖链深度: **load → 9 add → 1 fmsub → clamp → stream** (约 11 级)

**关键差异**: IPCC 将 9 个像素分成 4+1 个独立组，每组内部加法可并行执行，依赖链只有 2-3 级；本项目 9 次累加全部串行在 `sum` 寄存器上，形成 9 级加法依赖链。在 Arrow Lake 的宽发射架构上，IPCC 的 ILP 设计更好地利用了指令级并行。

#### 6.6.3 对齐处理对比

**IPCC**：一次性前置对齐。只在进入主循环前做一次标量对齐循环，将 `out` 指针对齐到 32 字节：
```cpp
int alignOffset = alignPtr - (out + width + 1);
for (int i = 0; i < alignOffset; ++i) { /* scalar */ }
// 之后所有 stream store 地址均对齐
```

**本项目**：每行独立对齐。在 `#pragma omp parallel for` 内每行都检测对齐：
```cpp
for (int i = 1; i < height; i++) {
    misalign = addr & 31;
    if (misalign != 0) { /* scalar prologue */ }
    // SIMD + stream store
}
```
→ 每行都执行分支判断 + 可能的标量循环，10410 列 × 5905 行 = 5905 次对齐检测。

#### 6.6.4 2x 循环展开效果分析

本项目 2x 展开理论上应减少循环开销 50%，但实际在本硬件上反而更慢。原因：

1. **寄存器压力**：2x 展开需要 ~14 个 YMM 寄存器（2×4 数据 + 3 常量 + 临时），接近 16 YMM 上限，编译器可能 spill 到栈
2. **指令缓存**：展开后循环体变大 (~100 条指令 vs IPCC 的 ~60 条)，可能超出 μop cache 容量
3. **乱序执行已足够**：Arrow Lake 的乱序窗口很大，1x 循环的 load latency 已被硬件预取和乱序执行隐藏，2x 展开的额外 ILP 无增量收益
4. **ICPC/ICC 编译器差异**：IPCC 原始优化报告使用 Intel 编译器 (ICC)，其自动向量化 + 循环展开策略与 GCC 不同

#### 6.6.5 公式等价性证明

两种公式数学等价：
```
本项目: 9 * center - (TL+TC+TR+ML+center+MR+BL+BC+BR)
       = 9*center - center - (TL+TC+TR+ML+MR+BL+BC+BR)
       = 8*center - sum_of_8_neighbors

IPCC:   8*center - (TL+TC+TR+ML+MR+BL+BC+BR)
       = 8*center - sum_of_8_neighbors
```
但本项目将 center 加入 sum 再 fmsub，多了一次依赖链上的加法。

#### 6.6.6 总结：为什么 IPCC 代码在本硬件更快

| 因素 | IPCC | 本项目 | 影响 |
|------|------|--------|------|
| 加法依赖链深度 | ~5 级 | ~11 级 | **关键差异** |
| 对齐开销 | 一次前置 | 每行一次 | 中 |
| 寄存器压力 | 低 (~8 YMM) | 高 (~14 YMM) | 中 |
| 指令缓存 | 紧凑 | 2x 展开体更大 | 低-中 |
| 软件预取 | 无 | 有 (T0 → L1) | 低（硬件预取已足够） |
| Load 数量 | 9 loads/8 elems | 9 loads/8 elems | 相同 |

**结论**：IPCC 的分组加法策略（将 9 个像素分入独立子树再合并）是关键优势，在本硬件上快约 7%。如果将 IPCC 的分组加法 + 本项目的 2x 展开组合，理论上可能进一步超越两者，但需注意寄存器压力。

## 七、尚未尝试的优化方向

### 高优先级

1. **P-core 精确绑定** ⭐⭐⭐
   - 当前 WSL2 无法区分 P-core/E-core
   - 在原生 Linux 上可用 `taskset -c <p-core-list>` 绑定
   - 预期额外 10-15% 提升

2. **AVX-512 版本** ⭐⭐⭐
   - Arrow Lake 是否支持 AVX-512 需确认
   - 如支持：一次处理 16 float，预期 1.5-2x SIMD 吞吐提升

### 中优先级

3. **大页内存** ⭐⭐
   - 减少 TLB miss（61M 像素 ≈ 244K 个 4KB 页）
   - `echo 1024 > /proc/sys/vm/nr_hugepages` + mmap MAP_HUGETLB

4. **多图像交叉验证** ⭐⭐
   - 题目要求用多个图像验证正确性
   - 已测试 IPCC.png → check.txt 完全一致

### 低优先级

5. **ICX/ICPX 编译器** ⭐
   - Intel oneAPI 编译器可能生成更好的代码
   - `icpx -O3 -xHOST -qopenmp -mavx2`

6. **2D cache tiling** ⭐
   - 行×列分块适配 L2 cache
   - 对超宽图像可能无明显收益
